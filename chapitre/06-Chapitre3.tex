\section{Architecture de l'application}

\noindent Dans cette section, nous présentons l'architecture adoptée pour notre application, en détaillant l'organisation physique et logique de notre système.

\subsection{Architecture physique}

\noindent Notre application suit une architecture distribuée trois tiers enrichie d'un service spécialisé. Cette organisation permet une séparation physique des composants, facilitant la scalabilité et la maintenance du système.

\noindent La figure 3.12 illustre le déploiement physique de notre application :

\begin{figure}[H]
    \centering
    \includegraphics[width=14cm, height=11cm]{images/Architecturephysique.PNG}
    \label{fig:arch_physique}
    \caption{Architecture physique de l'application}
\end{figure}

\noindent L'architecture se compose de plusieurs nœuds de déploiement :

\noindent \textbf{Environnement Client} : Les postes clients accèdent à l'application via un navigateur web standard qui charge l'interface utilisateur développée en React. La communication avec le serveur applicatif s'effectue via le protocole HTTPS à travers Internet, garantissant la sécurité des échanges.

\noindent \textbf{Serveur Applicatif} : Héberge la logique métier implémentée sous forme d'API REST (.NET Core). Ce serveur orchestre les communications avec les autres composants du système via HTTP/REST et gère l'authentification et l'autorisation des requêtes. Il sert de point d'entrée unique pour toutes les opérations métier.

\noindent \textbf{Serveur Base de Données} : Assure la persistance des données de l'application via un SGBD relationnel (SQL Server). Il communique avec le serveur applicatif via une connexion TCP/IP sécurisée. Cette séparation physique renforce la sécurité et permet une gestion indépendante des ressources de stockage.

\noindent \textbf{Serveur NLP} : Serveur dédié au traitement du langage naturel, déployé de manière indépendante avec un service Flask. Il reçoit les requêtes du serveur applicatif via HTTP/REST et communique avec l'API Gemini de Google via HTTPS pour l'analyse textuelle et la génération de recommandations.

\noindent \textbf{Services Externes} : APIs tierces hébergées dans le cloud (Stripe pour les paiements, Gemini pour l'IA), intégrées via des connexions HTTPS sécurisées. Ces services étendent les fonctionnalités du système sans nécessiter de déploiement local.

\noindent Cette architecture distribuée offre plusieurs avantages : scalabilité horizontale par réplication des serveurs, isolation des pannes, et possibilité de déployer chaque composant sur des infrastructures optimisées selon ses besoins spécifiques.

\subsection{Architecture logique}

\noindent L'architecture logique repose sur le patron MVC enrichi d'une approche microservices pour les fonctionnalités spécialisées. Cette organisation assure une séparation claire des responsabilités et facilite l'évolution du système.

\noindent La figure 3.13 illustre l'organisation logique de notre application :

\begin{figure}[H]
    \centering
    \includegraphics[width=14cm, height=11cm]{images/Architecturelogique.PNG}
    \label{fig:arch_logique}
    \caption{Architecture logique de l'application}
\end{figure}

\noindent L'utilisateur interagit avec le système via un navigateur qui héberge la couche présentation sous forme de composants React. Cette interface communique avec le backend via une couche d'APIs REST qui constitue le point d'entrée unique du système.

\noindent \textbf{APIs REST} : Ensemble d'endpoints exposés par les contrôleurs, organisés par domaine fonctionnel (authentification, gestion des audits, conformité, analyse textuelle). Cette couche assure le découplage entre le client et le serveur, permettant une évolution indépendante de chaque partie. Les échanges utilisent le format JSON pour la sérialisation des données.

\noindent \textbf{Couche Contrôleurs} : Implémentée via des contrôleurs .NET Core, elle reçoit et valide les requêtes HTTP entrantes. Elle gère les mécanismes d'authentification et d'autorisation basée sur les rôles, puis route les requêtes vers les services métier appropriés. Cette couche applique le principe de responsabilité unique en se limitant à l'orchestration des flux.

\noindent \textbf{Couche Métier} : Contient les services applicatifs et les entités du domaine métier. Elle encapsule l'ensemble des règles métier et coordonne les opérations complexes impliquant plusieurs entités. Cette couche reste indépendante des détails d'implémentation de la persistance et de la présentation, garantissant ainsi une meilleure testabilité et maintenabilité.

\noindent \textbf{Couche Accès Données} : Implémente le patron Repository pour abstraire l'accès à la base de données. Elle utilise Entity Framework Core comme ORM pour convertir les entités métier en structures de données persistantes et gère les transactions pour garantir la cohérence des données. Cette abstraction permet de changer de système de stockage sans impact sur les couches supérieures.

\noindent \textbf{Microservice NLP} : Service autonome développé avec Flask, exposant sa propre API REST. Il reçoit les demandes d'analyse textuelle depuis les contrôleurs principaux, effectue le traitement via l'API Gemini, et retourne les résultats enrichis. Cette séparation en microservice permet une scalabilité indépendante et facilite l'évolution des fonctionnalités d'analyse sans impact sur le reste du système.

\noindent Cette architecture applique les principes SOLID et respecte la séparation des préoccupations. Le couplage faible entre les couches facilite les tests unitaires et l'évolution progressive du système. L'approche microservices pour les fonctionnalités spécialisées permet une meilleure résilience et une gestion optimale des ressources.
